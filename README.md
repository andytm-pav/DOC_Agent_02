# ИИ-агент «Документовед» v2.9.0

Локальный ИИ-агент: приём «свалки» файлов → извлечение → картотека → вопросы с
grounding (без галлюцинаций) → воспроизведение документов → A2A. Без облака,
без телеметрии. Python 3.11+ (рекомендуется 3.12).

**Все настройки — в `config/config.yaml`, секреты — в `.env`.**

---

## Запуск на Windows в PyCharm (5 минут)

1. **Распакуйте архив** в папку без пробелов в пути (например `C:\dev\document-agent`).

2. **Создайте проект в PyCharm:** `File → Open…` → выберите папку проекта.

3. **Создайте интерпретатор:** `File → Settings → Project → Python Interpreter →
   Add Interpreter → Add Local Interpreter → Virtualenv Environment → New`:
   - Base interpreter: Python 3.12
   - Location: `C:\dev\document-agent\.venv`
   - Нажмите OK.

4. **Установите зависимости** — в терминале PyCharm (Alt+F12):

   ```bat
   pip install -e ".[dev]"
   copy .env.example .env
   ```

   (либо просто запустите `setup.bat` один раз до PyCharm — он всё сделает сам)

5. **Запуск:** откройте `src/doc_agent/main.py` → правый клик → `Run 'main'`.
   Рабочая папка должна быть корнем проекта (Run → Edit Configurations →
   Working directory: `C:\dev\document-agent`).
   Альтернатива в терминале: `uvicorn doc_agent.main:app --host 0.0.0.0 --port 8000`
   или просто `run.bat`.

6. Откройте **http://localhost:8000** — чат и кнопка «Загрузить» (DD-1).
   Логин по умолчанию: `admin` / `admin` (меняется в `.env`).

## Подключение внешней модели по API (с ключом)

Откройте `config/config.yaml`, секция `llm`:

```yaml
llm:
  provider: openai_compatible          # любой OpenAI-совместимый API
  base_url: "https://api.openai.com/v1"
  api_key: "${LLM_API_KEY}"            # ключ берётся из .env
  model_main: "gpt-4o-mini"
  model_light: "gpt-4o-mini"
```

Впишите ключ в файл `.env` (лежит рядом с config):

```
LLM_API_KEY=sk-ваш-ключ
```

Примеры `base_url`:
| Провайдер | base_url |
|---|---|
| OpenAI | `https://api.openai.com/v1` |
| OpenRouter | `https://openrouter.ai/api/v1` |
| Z.ai (GLM) | `https://api.z.ai/api/paas/v4` |
| Локальный LM Studio | `http://localhost:1234/v1` |
| Локальный Ollama | `http://localhost:11434` + `provider: ollama` |

Режимы `provider`:
- `openai_compatible` — внешняя модель по API-ключу (для вашей проверки);
- `ollama` — локальный офлайн-режим из ТЗ (запуск: `docker compose up -d ollama`,
  затем `python scripts/pull_models.py`);
- `none` — полностью без LLM: классификация по правилам `config/rules.yaml`,
  ответы — только точные цитаты из файлов. Всё это работает офлайн «из коробки».

> Если ключ/сеть недоступны — агент НЕ падает: после 2 попыток (E003) он
> автоматически возвращается к правилам и экстрактивным ответам (E004).

## Локальные эмбеддинги без ключа и интернета (sentence_transformers)

Настоящая семантическая модель работает ЛОКАЛЬНО: без ключей, без отправки
документов куда-либо, без интернета — после первого скачивания модели.
Подходит, если нет ключа bigmodel.cn или документы не должны покидать
компьютер.

**Шаг 1.** Установите ML-пакеты (один раз; тянет torch, ~2 ГБ диска,
~1 ГБ RAM при работе):

```bat
pip install -e ".[ml]"
```

**Шаг 2.** В `config/config.yaml` переключите бэкенд:

```yaml
embeddings:
  backend: sentence_transformers
  model: "intfloat/multilingual-e5-small"   # 384 dims, ~120 МБ — рекомендуется
  # device: ""          # "" = авто (CUDA если есть, иначе CPU); "cpu" — принудительно
  # dimensions: 0       # 0 = взять фактическую из модели; смена = новая коллекция
  # query_prefix: "query: "       # e5-моделям ОБЯЗАТЕЛЬНО; для bge-m3 поставьте ""
  # passage_prefix: "passage: "   # и здесь ""
```

**Шаг 3.** Перезапустите агента и загрузите файлы. При ПЕРВОМ запуске
модель скачивается с huggingface.co (~470 МБ, одна пара минут), затем
живёт в кэше (`%USERPROFILE%\.cache\huggingface`) и работает офлайн.
Если huggingface.co отдаёт медленно — перед запуском задайте зеркало:

```bat
set HF_ENDPOINT=https://hf-mirror.com
```

**Скорость на CPU (замерено на e5-small, чанки ~1800 симв., батч 32):**

| Железо | Скорость | 1 000 чанков | Вопрос в чате |
|---|---|---|---|
| 2 старых ядра Xeon (тест) | ~6 чанков/с | ~3 мин | ~20 мс |
| Типичный офисный ПК (4-8 ядер) | в 3-5 раз быстрее | ~40-60 с | ~10 мс |

Вывод: скорость загрузки свалки на CPU приемлема (ингест и так занят
извлечением текста и LLM-классификацией), ответ в чате не замедляется.
Тяжёлая bge-m3 (1024 dims, качество выше) на CPU в 5-8 раз медленнее
e5-small — берите её при наличии GPU или через Ollama.

**Качество vs API (embedding-3 @ bigmodel.cn):** у e5-small семантика
слабее (384 dims против 1024), но гибридный поиск v2.7 (BM25 + вектор +
морфология) и контекстные преамбулы v2.8 компенсируют бо´льшую часть
разницы. Рецепт выбора: есть ключ — API (`backend: auto` + блок
`embeddings.api`); нужен полный офлайн — `sentence_transformers`.

**Важно:** смена backend/модели/размерности создаёт НОВУЮ коллекцию
(`vector.auto_collection_suffix: true`) — переиндексируйте файлы
(админ-панель → «Полная переиндексация»). Старая коллекция остаётся
нетронутой: вернуть прежний бэкенд можно обратной сменой конфига.
Проверить фактический бэкенд/устройство/размерность — админ-панель,
блок `diagnostics.embeddings`.

## Что нового в v2.8: контекстные чанки (Anthropic), отказ как фича, честные ошибки API

1. **Контекстуальные преамбулы чанков** (Contextual Retrieval, Anthropic 2024;
   промышленно +18 п.п. recall@5 на вопросах-синтезах). В начало КАЖДОГО чанка
   перед эмбеддингом и индексацией добавляется контекст:
   `[имя файла | Лист: X | Раздел: Y > Z | однострочная заметка о документе]`.
   Заметка — 1 LLM-вызов на файл (кэшируется в описании файла; при сбое —
   fallback из метаданных классификатора), путь заголовков — по дереву
   документа без LLM (`chunking.context_note`, `note_max_chars`,
   `headings_in_prefix`). После включения нужна переиндексация.
2. **Отказ как полноценная фича** (анти-галлюцинация). Если ретрив вернул
   только слабые сигналы — лучший векторный косинус ниже
   `qa.refuse_vector_below` (0.35) И лучшее лексическое перекрытие ниже
   `qa.refuse_lexical_below` (0.12) — LLM не вызывается вовсе: детерминированный
   честный отказ «в загруженных документах информации не найдено» + подсказка
   похожих файлов. Сильный хотя бы один сигнал — отвечаем; автодочтение по
   плану сохранено.
3. **Честные ошибки API.** Тело ошибки провайдера теперь попадает в лог/статус
   (раньше голое «400 Bad Request» скрывало причину — например «model not
   found» у эмбеддингов).
4. **Rate-limit backoff (429/5xx).** Ретраи с учётом Retry-After для LLM
   (`llm.rate_limit_retries`, `rate_limit_backoff_sec`) и эмбеддингов
   (`embeddings.api.rate_limit_retries`) — бесплатный glm-4.5-flash малыми
   RPM больше не валит очередь ингеста потоком 429-х.
5. **Проверено запросами (v2.8): у МЕЖДУНАРОДНОГО api.z.ai НЕТ эмбеддингов**
   (в API-docs только chat/agents/image/video; POST /embeddings даёт 400).
   Эмбеддинги Zhipu (embedding-3) — только на open.bigmodel.cn (гибрид)
   или локально: `backend: sentence_transformers` либо Ollama
   (`http://localhost:11434/v1`, model `bge-m3`, 1024 dims).

   Гибрид с bigmodel.cn — ключ Zhipu впишите в `.env` ОТДЕЛЬНОЙ переменной
   (ключ bigmodel.cn не совпадает с ключом z.ai), затем подключите в
   `config.yaml` → `embeddings.api`:

   ```yaml
   embeddings:
     api:
       model: "embedding-3"
       base_url: "https://open.bigmodel.cn/api/paas/v4"
       api_key: "${EMBEDDING_API_KEY}"   # переменная из .env (см. .env.example)
       dimensions: 1024
   ```

## Что нового в v2.7: промышленный ретрив — «агент не видит и галлюцинирует» исправлено

Диагноз по реальному диалогу («какой материал по вилоновской?» приносил чанки
Конкурсной документации/Аэр с «уверенностью 0.11») выявил пять корневых причин.
Все исправлены по промышленным практикам (гибрид BM25+вектор+RRF — Elastic/
Weaviate/Qdrant; Contextual Retrieval — Anthropic 2024; Snowball-стемминг —
стандарт морфологии для поисковых систем):

1. **Псевдо-эмбеддинги заменены настоящими.** `embeddings.backend: auto` —
   если у провайдера LLM есть /embeddings (например, Z.ai `embedding-3`),
   используются настоящие семантические эмбеддинги; без ключа — офлайн
   hashing. Hashing — это НЕ семантика, а лексическое совпадение токенов.
2. **Морфология.** Вендорен Snowball-стеммер (русский, чистый Python, без
   зависимостей): «вилоновской» теперь находит «Вилоновская», «материалов» —
   «материал» — в BM25, реранкере, grounding и hashing-эмбеддингах
   (`embeddings.stem_lexical`). Пережатые формы («материал»→«материа»)
   компенсируются префиксной совместимостью стеммов.
3. **BM25 видел не весь корпус.** Молчаливый `LIMIT 4000` без ORDER BY
   выбрасывал из поиска чанки поздних файлов. Теперь весь корпус кандидатов
   (`retrieval.max_chunks`).
4. **Отсев мусора до LLM.** Векторные хиты слабее 55% лучшего score
   выкидываются (`retrieval.vector_relative_cutoff`); фрагменты с нулевым
   лексическим перекрытием с вопросом не идут в промпт
   (`rerank_drop_zero_overlap`); файлы с объектом в имени получают буст
   (`retrieval.filename_boost`); репортеру прямо запрещено отвечать из
   нерелевантных фрагментов (промпт reporter.txt).
5. **Табличный чанкинг xlsx.** Чанки режутся ПО СТРОКАМ (раньше строка
   «Унифлекс ЭПП… рул» обрывалась посередине), в преамбуле каждого чанка —
   имя файла и лист, шапка колонок повторяется в каждом чанке; строки данных
   сериализуются как «Заголовок: значение» (`chunking.table_aware`).

Плюс: **уверенность откалибрована** (смесь retrieval-score и grounding,
`groundrails.confidence_*_weight`); **изоляция векторных пространств**
(`vector.auto_collection_suffix`) — старые и новые эмбеддинги больше не
смешиваются в одной коллекции; планировщику вменено исправлять опечатки в
поисковом запросе (LLM-first, без привязок к фразам).

**Начисто:** `python scripts/reset_database.py --yes` — полный сброс (БД,
история чата, архивы памяти, векторный индекс, файлы; `--keep-files` /
`--history-only` / `--vectors-only`). Запускать при остановленном сервере.
После обновления выполните сброс или «Полная переиндексация», чтобы новые
чанки/эмбеддинги легли поверх всех файлов.

## Что нового в v2.6.1: точность по сметам — «агент не видит файл» исправлено

Причины проблем из практики («что в сметах по Вилоновской» находило чужие
документы, «нужно материалы» давало куски с уверенностью 0–0.17):

1. **Строки смет не содержат имени файла.** В xlsx-смете текст — это строки
   «1; Насечка поверхности; 584; м2»; слово «Вилоновская» есть только в
   названии файла и шапке. Поиск по содержимому (BM25 и векторный) не мог
   связать вопрос со сметой. Теперь каждый чанк несёт преамбулу
   `[имя_файла]` (конфиг `chunking.filename_prefix`) — сметы находятся.
2. **Названный файл уходил в кусочный поиск.** Правило планировщика
   «факт внутри документа → search_content, даже если назван файл»
   заменено: документ назван → `read_file` целиком (материалы, работы,
   суммы — из полного текста, а не из 5 кусков). Группа файлов по объекту
   («что в сметах по X») — чтение всех подходящих (до 6, `qa.deep_read_max_files`).
3. **«Уверенность: 0» при хорошем ответе.** Формула брала МИНИМУМ score из
   5 фрагментов — один слабый кусок обнулял всё. Теперь среднее TOP-3
   (`groundrails.confidence_top_k`).
4. **«Полная переиндексация» теперь переобрабатывает файлы** по текущим
   настройкам (извлечение + чанки + эмбеддинги), а не только
   переэмбеддиррует старые чанки — иначе новые настройки чанкинга не
   действовали на уже загруженные файлы.

После обновления: админ-панель → «Полная переиндексация» (один раз), чтобы
преамбула имён появилась в уже загруженных файлах.

## Что нового в v2.6: чат стал LLM-first — никаких жёстких привязок к фразам

**Как раньше (v2.5):** вопрос разбирался ключевыми словами («сколько…», «покажи
все…», «прочитай…») — нестандартная формулировка проскакивала мимо механизмов
и получала «НЕТ ДАННЫХ».

**Как теперь:**

```
вопрос на естественном языке
   → 1. LLM-планировщик: понимает, ЧТО нужно (видит картотеку и контекст беседы),
        возвращает план: механизм + термы + тип + файлы + поисковый запрос
   → 2. детерминированный механизм: картотека/подсчёт (SQL), чтение файла
        целиком или гибридный поиск по содержимому (RAG)
   → 3. LLM-синтез: ответ обёрнут в естественный язык (тот же LLM)
```

- С ЛЛМ спрашивают «посчитай мне акты по вилоновской», «а что там по старому
  городу?», «открой смету и расскажи» — агент сам поймёт и запустит нужный
  механизм. Приветствия/благодарности получают живой ответ (action=direct),
  а не «НЕТ ДАННЫХ».
- Списки и подсчёты картотеки тоже формулирует LLM (synthesis.txt), при этом
  числа и [file_id:N] копируются из данных БД без изменений.
- Планировщик использует model_light (быстро), промпт —
  `config/prompts/planner.txt`, всё настраивается секцией `planner`
  (действия, лимиты, включение, прямой ответ).
- Отказобезопасность: сбой LLM/не-JSON → детерминированный fallback по
  ключевым словам (qa.*) → обычный RAG. При `llm.provider: none` агент
  работает офлайн как раньше.

### Эмбеддинги: что используется сейчас и как включить настоящие

- По умолчанию (`embeddings.backend: hashing`) векторизация — это
  детерминированный feature-hashing (384 размерности): токены текста
  хэшируются в вектор. ЭТО НЕ НЕЙРОСЕТЬ и не модель: смысловая близость
  почти не ловится, поиск держится в основном на BM25. Никакой внешней
  модели при этом не подключено — верно.
- Новое в v2.6 — `embeddings.backend: api`: НАСТОЯЩИЕ эмбеддинги через
  OpenAI-совместимый `/embeddings` ТОГО ЖЕ провайдера и ТОГО ЖЕ ключа,
  что и основная модель (отдельное подключение не нужно):

  ```yaml
  embeddings:
    backend: api
    api:
      model: "embedding-3"   # для Z.ai/Zhipu; OpenAI: text-embedding-3-small
  ```

  ВАЖНО: после смены backend смените `vector.collection` (например
  `chunks_e5`) и переиндексируйте — в коллекции лежат векторы старой
  размерности.
- Третий вариант — локальная модель без интернета:
  `pip install -e ".[ml]"` + `backend: sentence_transformers`
  (intfloat/multilingual-e5-small, ~470 МБ на CPU).

## Что нового в v2.5: агент знает картотеку, считает файлы и читает их целиком

**Проблема.** «Сколько файлов обработано?» — «НЕТ ДАННЫХ»; «покажи все КС2» —
показывает договоры; агент не знает, что лежит в картотеке, и не может
прочитать файл целиком.

**1. Подсчёт файлов (без LLM, из БД):**
- «сколько файлов обработано?» → всего + разбивка по типам;
- «сколько договоров по вилоновской 23?» → поиск по названиям, типам
  (алиасы doc_type), номерам и городу; если по названиям 0 — по содержимому
  чанков (лимиты и вкл/выкл: `qa.count_content_fallback`).

**2. Поиск по названиям И типам:** «покажи все КС2» находит и файлы со «КС2»
в имени, и файлы с `doc_type: ks2` (`qa.doc_type_aliases`).

**3. Исправлена морфология поиска:** короткие токены и токены с цифрами
(«кс2», «23») ищутся только точным вхождением (`qa.name_exact_max_len`).
Раньше «кс2» сокращался до префикса «к» (совпадало всё подряд), а «23» до «2»
(совпадало «№27-07-2026») — отсюда «договоры вместо КС2».

**4. Глубокое чтение файла (полный текст в LLM вместо векторных обрывков):**
- по явной просьбе: «прочитай файл <имя>», «что в документе …?»
  (`qa.deep_read_cues`), до `qa.deep_read_max_files` файлов и
  `qa.deep_read_max_chars` символов;
- автодочтение: если обычный поиск ответил «НЕТ ДАННЫХ», но вопрос указывает
  на конкретный файл — агент сам перечитывает его целиком
  (`qa.deep_read_on_no_data`);
- промпт — `config/prompts/deep_read.txt`.

**5. Картотека в промпте репортера:** на каждый вопрос агенту передаётся
список файлов с типами и краткими описаниями (`qa.catalog_*`) — он «знает»,
что загружено, и в ответах ссылается на нужные файлы.

**6. Умный отказ:** вместо голого «НЕТ ДАННЫХ» — подсказка похожих файлов
картотеки и фраза «спросите „прочитай файл …"» (`qa.no_data_suggest`).

**7. Лимиты убраны:** `ingest.max_files_per_scan: 0` и `sorting.max_files: 0`
— 0 означает «без лимита» (в v2.4 разгребание останавливалось на 500 файлах).

**8. UI:** новые метки ответов (🧮 подсчёт, 🔍 поиск, 📖 прочитан целиком),
обновлены приветствие и подсказка «что ты можешь?».

## Исправления v2.4.1: reasoning-модели (glm-4.5-flash) и сервисные ответы

**Проблема 1.** Reasoning-модели (GLM-4.5*, GLM-4.6 через Z.ai/Zhipu) возвращают
JSON обёрнутым в размышления `<think>…</think>` и markdown-ограждения
```` ```json … ``` ````, из-за чего строгий парсер падал («LLM вернул не-JSON»)
и разгребание свалки уходило в fallback «Файлы PDF/TXT» вместо тематических папок.

**Исправление:** во всех точках разбора JSON (разгребание, классификация,
сжатие контекста) теперь устойчивое извлечение — переживает `<think>`,
ограждения, текст вокруг JSON, «висячие» запятые и python-стиль.

**Рекомендация для glm-4.5-flash** — отключите «размышления» в config.yaml
(ответы станут быстрее и чище; ключ — в `.env`, LLM_API_KEY):

```yaml
llm:
  provider: openai_compatible
  base_url: "https://api.z.ai/api/paas/v4"   # или https://open.bigmodel.cn/api/paas/v4
  api_key: "${LLM_API_KEY}"
  model_main: "glm-4.5-flash"
  model_light: "glm-4.5-flash"
  # Доп. поля тела запроса. Для GLM-4.5*/4.6 отключает размышления:
  extra_body: {"thinking": {"type": "disabled"}}
```

**Проблема 2.** На вопросы «покажи все файлы», «какие файлы есть по …»,
«что ты можешь?» агент отвечал «НЕТ ДАННЫХ» — это не «тупость» модели:
строгий RAG-репортер обязан отвечать только по содержимому файлов, а сервиса
для мета-вопросов не было.

**Исправление:** сервисные ответы (секция `qa` в config.yaml, ключевые слова
настраиваются):
- «покажи все файлы» / «какие файлы есть по вилоновской» — список загруженных
  файлов из картотеки, в т.ч. поиск по НАЗВАНИЯМ файлов (с лёгкой морфологией);
- «что ты можешь?» — подсказка из `config/prompts/help.txt`;
- ответы детерминированы (без LLM), помечаются чипом «📋 список файлов /
  💡 подсказка» и сохраняются в историю чата.

**Также:** UserWarning openpyxl («Print area cannot be set…») больше не
забивают консоль при импорте свалок — флаг `ingest.suppress_extract_warnings: true`.

## Импорт свалки файлов из папки (новое в v2.1)

Два способа загрузки документов — работают одновременно:

1. **Папка со свалкой.** На главной странице (чат) есть блок
   «Импорт свалки из папки»: укажите путь (например `D:/Свалка_документов`)
   и нажмите «Импортировать папку». Агент обойдёт папку (опционально —
   включая подпапки), примет все поддерживаемые файлы, пропустит дубликаты
   (dedup по sha256) и покажет сводку: принято / дубликаты / не поддерживаются /
   ошибки. Повторный импорт той же папки безопасен — всё уйдёт в дубликаты.
2. **По одному, как раньше.** Перетаскивание файла в Drop-зону или кнопка
   «Загрузить файл» — без изменений.

Настройки импорта — в `config/config.yaml`, секция `ingest`:

```yaml
ingest:
  folder_paths: ["D:/Свалка_документов"]  # подставится в поле UI автоматически
  recursive: true                          # обходить вложенные подпапки
  max_files_per_scan: 1000                 # лимит документов за один импорт
  supported_extensions: [pdf, docx, xlsx, ...]  # что брать из папки
```

API: `POST /files/scan-folder` с телом `{"path": "...", "recursive": true}`
(под JWT). Источник файлов помечается как `source: folder` — видно в картотеке.

## Разгребание свалки по тематическим папкам (новое в v2.3)

Агент сам наводит порядок в свалке: создаёт по указанному пути папку
(по умолчанию — рядом со свалкой, `<свалка>_разобрано/Разобранная свалка_<дата-время>`),
читает содержимое каждого файла и **сам придумывает названия тематических
подпапок** — понятные человеку («Договоры аренды», «КС-2 и КС-3», «Переписка»),
после чего **копирует** файлы по этим папкам (свалка не меняется).

**Как пользоваться (UI):** на главной странице блок «Разобрать свалку
по папкам» → укажите папку свалки, при желании — куда сложить результат
(пусто = рядом со свалкой) → «Разобрать свалку». Виден прогресс по фазам
(скан → чтение → названия → раскладка) и итог: список папок и число файлов.

**Как пользоваться (API):**

```bash
# запустить разбор (под JWT или X-API-Key)
curl http://localhost:8000/files/sort-folder -H "Authorization: Bearer <token>" \
     -H "Content-Type: application/json" \
     -d "{\"path\":\"D:/Свалка_документов\",\"output_path\":\"D:/Разобранное\"}"
# -> {"job_id": "...", "state": "running"}

# опросить статус до state=done
curl http://localhost:8000/files/sort-folder/<job_id> -H "Authorization: Bearer <token>"
```

В ответе: `run_dir` (созданная папка), `folders` (список папок с файлами),
`mode` (copy/move), `llm_named`/`fallback_used`, счётчики.

**Откуда берутся названия.** Используется LLM из секции `llm` (та же внешняя
модель по API-ключу): файлы отправляются пакетами, модель возвращает строгий
JSON с папкой для каждого файла. Промпт — `config/prompts/sorting.txt`.
Запрещённые в именах символы очищаются, число папок ограничено
(`max_folders`, лишнее — в «Прочее»). Если LLM отключён (`provider: none`)
или недоступен — детерминированный fallback из конфига: папки по расширениям
(`by_extension`) или всё в одну папку (`single`). Разбор при этом не ломается.

Настройки — в `config/config.yaml`, секция `sorting` (все без хардкода):

```yaml
sorting:
  enabled: true
  default_output_suffix: "_разобрано"   # куда по умолчанию
  move_files: false                     # false = копировать, true = перемещать
  max_files: 500                        # лимит за один запуск
  max_folders: 20                       # максимум тематических папок
  misc_folder: "Прочее"
  fallback: "by_extension"              # без LLM: by_extension | single
  batch_size: 20                        # файлов в одном запросе к LLM
```

## Память чата: история, контекст и архив памяти (новое в v2.4)

**История не пропадает.** Все сообщения чата хранятся в БД: при обновлении
страницы или возврате в чат история загружается заново — до тех пор, пока вы
не нажмёте «🧹 Очистить историю». Персонально для каждого пользователя.

**Контекст и его очистка.** Последние сообщения (число настраивается,
`chat.context_max_messages`) образуют актуальный контекст — агент учитывает
его при ответах («повтори…», «а теперь по другому договору…»). Кнопка
«📦 Очистить контекст (в архив)» сворачивает текущую беседу в **сжатую
памятку** (LLM-суммаризация; без LLM — выжимка из вопросов) и отправляет её
в «Архив памяти». Прошлый контекст больше НЕ занимает контекстное окно
актуальной беседы, а история на экране остаётся.

**«Вспомни…».** Спросите «Вспомни, когда мы загружали такие-то файлы?» —
агент найдёт памятку в архиве и кратко расскажет, что обсуждалось (в ответе
пометка «📦 из архива памяти»). Ключевые слова перехвата — в конфиге
(`chat.recall_keywords`). Список памятек виден по кнопке «🗂 Архив памяти».

**Строка статуса агента.** Над чатом всегда видно, что происходит:
состояние БД/вектора/модели (🟢/🔴), имя модели и провайдера, очередь
обработки файлов, фазы разгребания свалки. Во время ответа — таймер
«Думаю… (N с)».

**Диагностика для разработчика.** В разделе «Админ» — блок «Диагностика»:
статус модели (провайдер, base_url, модель, есть ли ключ), состояние БД и
вектора, очередь задач, последние действия аудита и последние ошибки из
лога. Кнопка «Скопировать» кладёт весь отчёт в буфер — пришлите его при
разборе багов.

API:

```bash
curl http://localhost:8000/chat/history -H "Authorization: Bearer <token>"   # история
curl http://localhost:8000/chat/archives -H "Authorization: Bearer <token>"  # памятки
curl -X POST http://localhost:8000/chat/clear-history -H "Authorization: Bearer <token>"
curl -X POST http://localhost:8000/chat/clear-context -H "Authorization: Bearer <token>"
curl http://localhost:8000/status -H "Authorization: Bearer <token>"         # статус агента
curl http://localhost:8000/admin/debug -H "Authorization: Bearer <admin-token>"  # диагностика
```

Настройки — в `config/config.yaml`, секция `chat` (история, размеры контекста,
ключевые слова «вспомни», периоды опроса); промпты суммаризации и «вспомни» —
`config/prompts/context_summary.txt` и `config/prompts/context_recall.txt`.

## Доступ к API агента из внешних систем по ключу (новое в v2.2)

Внешние программы (скрипты, n8n, 1С, другие агенты) могут вызывать все API
агента **без логина** — по API-ключу.

**Шаг 1.** В файле `.env` задайте ключ:

```
EXTERNAL_API_KEY=my-super-secret-key-123
```

**Шаг 2.** В `config/config.yaml` секция `auth.api_keys` уже подключает его:

```yaml
auth:
  api_keys:
    - key: "${EXTERNAL_API_KEY}"   # ключ из .env
      name: external-system        # имя вызывающей стороны (попадает в audit_log)
      role: user                   # user | admin
    # можно добавить несколько ключей с разными ролями
```

**Шаг 3.** Передавайте ключ в заголовке `X-API-Key` (или `Authorization: Bearer <ключ>`):

```bash
# вопрос по картотеке
curl http://localhost:8000/query -H "X-API-Key: my-super-secret-key-123" ^
     -H "Content-Type: application/json" ^
     -d "{\"q\":\"Покажи все КС2 по договору 123\"}"

# загрузка файла
curl http://localhost:8000/files/upload -H "X-API-Key: my-super-secret-key-123" -F "file=@акт.docx"

# импорт папки со свалкой
curl http://localhost:8000/files/scan-folder -H "X-API-Key: my-super-secret-key-123" ^
     -H "Content-Type: application/json" -d "{\"path\":\"D:/Свалка_документов\"}"

# картотека с фильтрами
curl "http://localhost:8000/card?doc_type=ks2&contract_no=123" -H "X-API-Key: my-super-secret-key-123"
```

Дополнительно:
- ключ принимают **все** защищённые эндпоинты, включая `/a2a` (внешний A2A-клиент
  идентифицируется как `api:<name>`);
- вызовы с ключом пишутся в audit_log с именем из `name`;
- `role: admin` даёт ключу доступ к `/admin/*` — выдавайте осторожно;
- отключить ключ — просто очистите `EXTERNAL_API_KEY` в `.env`;
- `GET /health` остаётся открытым (мониторинг без ключа);
- сравнение ключей timing-safe (secrets.compare_digest).

## Ошибки и деградация (раздел 10 ТЗ)

E001 формат не распознан · E002 OCR < 0.50 → просим скан ≥300 dpi ·
E003 LLM вернул не-JSON → retry 1 раз · E004 LLM недоступен → правила/цитаты ·
E005 ChromaDB недоступна → BM25 + lite-store · E006 > 500 МБ ·
E007 XML сметы не парсится → description_only · E008 галлюцинация > 30 % →
partial · E009/E010 → 401/403.
